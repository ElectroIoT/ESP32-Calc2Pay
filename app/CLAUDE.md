# CLAUDE.md — app/

Instructions for Claude (or any AI agent) working in this folder. Read `MEMORY.md` in this folder first, then this file.

## What this folder is

A **new** Flutter mobile app (package `calc2pay_companion`) for the Calc2Pay BLE companion app. Builds clean (`flutter analyze`, `flutter test`, `flutter build apk --debug` all pass) but has never been run against real Calc2Pay hardware. See `MEMORY.md` for exact state.

## Folder layout

```text
app/
  pubspec.yaml
  lib/ble/calc2pay_ble_uuids.dart     ← BLE contract, mirrors ../firmware/include/ble_uuids.h
  lib/ble/calc2pay_ble_service.dart   ← flutter_blue_plus wrapper
  lib/models/                         ← merchant_config.dart, device_status.dart (JSON models)
  lib/screens/scan_screen.dart        ← permissions + scan + connect
  lib/screens/device_home_screen.dart ← status view + nav to settings
  lib/screens/merchant_config_screen.dart ← read/edit/write merchant config
  lib/ble/generic_ble_printer_service.dart ← SEPARATE BLE connection: standalone thermal printer, not the Calc2Pay device
  lib/screens/ble_printer_screen.dart ← scan/connect/test-print UI for that separate printer
  lib/main.dart
  android/, ios/                      ← generated by `flutter create`, Android BLE permissions added
```

**Do not confuse the two BLE connections.** `calc2pay_ble_service.dart`/`calc2pay_ble_uuids.dart` talk to the Calc2Pay ESP32 device using a fixed, allocated GATT contract. `generic_ble_printer_service.dart` talks to an unrelated, vendor-specific BLE thermal printer with no fixed UUID — it scans broadly and heuristically picks a writable characteristic. They are independent connections that can coexist; never merge their UUID handling or assume one implies the other is connected.

## Hard rules

1. **Never copy code from, or treat as a dependency, the existing closed-source Flutter app at `D:\My Project\Android\Calc2Pay`.** That is a different, unrelated, closed product (a billing/QR app, not a BLE device companion). This project must be open source and independently licensed — do not introduce a dependency on private/closed code. UI *inspiration* (visual layout ideas) is fine; shared code, shared package name, or shared repo is not.
2. **BLE GATT UUIDs come from `../firmware/`, not from this folder.** If firmware hasn't allocated a UUID for something you need, that's a cross-folder blocker — flag it, don't invent a UUID here and hope firmware matches later.
3. **Rev-1 has no backend and no payment confirmation.** Don't build cloud sync, accounts, or a "payment succeeded" UI state — the hardware has no channel to confirm a UPI payment actually completed (see `../hardware/01-DESIGN-REVIEW.md` §17). A QR being displayed or scanned is not proof of payment; the app must not imply otherwise.
4. Keep the app's scope to what `README.md` states for Rev-1: BLE connect, merchant config push, read-only status. Don't add features "while I'm in here" — this is a companion utility, not the product's main app.

5. **`lib/ble/calc2pay_ble_uuids.dart` must always match `../firmware/include/ble_uuids.h` exactly.** If you change one, change the other in the same commit and update both `MEMORY.md` files.
6. **This has never been tested against real hardware.** Don't describe BLE features as "working" beyond "compiles and connects to whatever GATT peripheral matches the UUIDs" — verify against the actual firmware once it's flashed before calling anything proven.

## When continuing implementation

- Run `flutter analyze` and `flutter test` before and after changes; run `flutter build apk --debug` after any dependency or platform-config change to confirm the build still produces an installable APK.
- Update `MEMORY.md`'s "Known gaps" and "Current state" as soon as something is verified against real hardware (or a gap is closed) — don't let it go stale.
